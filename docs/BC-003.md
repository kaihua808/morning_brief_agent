# BC-003｜测试依附生产入口，重构入口后断言静默失效

> 状态：已解决
> 发现日期：2026-09-01
> 归因层：测试结构缺陷

## 发现来源

代码审查。整理 `fund_metrics.py` 时发现，文件里虽然保留了 `test_calculate_period_change()`，但新的 `main()` 已经不再调用它，因此日常运行不会执行两条 `assert`。

## 触发条件

版本 `a72bf86` 中，测试函数和业务入口写在同一个生产文件：

```python
def test_calculate_period_change():
    assert ... == 5.00
    assert ... == -5.00

def main():
    test_calculate_period_change()
```

随后为生成正式基金 JSON 重写 `main()` 时，入口职责发生变化。如果保留测试函数却忘记调用，源码仍然可以正常运行，但断言已经失效。

## 实际行为

```text
python fund_metrics.py
→ 正常输出指标
→ 不运行旧 assert
→ 即使区间变化函数以后出错，生产入口也可能继续成功退出
```

问题没有产生显式报错，因此比“测试直接失败”更难发现。

## 期望行为

- 测试不依赖业务入口是否主动调用；
- 执行统一测试命令时自动发现所有测试；
- 生产入口只负责运行产品，不承担启动测试的职责；
- 重构 `main()` 不应让测试覆盖静默消失。

## 影响与风险

- 两条断言看起来仍在文件中，容易形成“这个函数已经有测试”的虚假信心。
- 如果计算公式被改坏，直接运行生产脚本可能仍返回退出码 0。
- 测试与业务代码混在一起，使后续重构难以判断哪些代码可以删除。

## 根因

测试的执行条件不是测试框架发现，而是生产入口中的一次普通函数调用：

```text
存在测试函数 ≠ 测试会执行
main() 不调用测试函数 → 测试静默失效
```

根因不是 `assert` 本身，而是测试生命周期依附在会频繁变化的生产入口上。

## 处理方案

- 将测试迁移到 `tests/test_fund_metrics.py`；
- 使用标准库 `unittest` 组织测试类与测试方法；
- 使用 `python -B -m unittest discover -s tests` 统一发现并执行；
- 删除生产源码中不再执行的旧测试函数；
- 为区间变化、区间位置和最大回撤分别建立固定输入测试。

## 回归验证

独立测试现已覆盖：

- 上涨与下跌区间变化；
- 当前值位于区间中部；
- 最高值等于最低值时拒绝计算；
- 峰值必须先于低点的最大回撤；
- 单调上涨时最大回撤为 0。

当前结果：

```text
Ran 59 tests
OK
```

`fund_metrics.py` 的 `main()` 可以继续变化，不会决定这些测试是否执行。

## 遗留限制

- 当前项目尚未配置 GitHub Actions，远端提交不会自动运行测试。
- 开发者仍需要在提交前主动执行统一测试命令。
- 59 条测试主要覆盖确定性代码；真实 Model 输出仍需要单独的手工或在线评测。
