# BC-002｜Tool 参数解析失败时，基金晨报程序拒绝生成并给出误导性诊断

> 状态：核心链路已解决，诊断细分仍待完善
> 发现日期：2026-09-02
> 归因层：SDK 兼容性边界；次要问题为错误诊断不准确

## 发现来源

真实端到端运行。本地 `build_fund_brief("006131")` 已能返回 `normal + completed`，但运行 Agent 入口仍然失败。

## 触发条件

- 命令：`python -B fund_main.py 006131`
- 基金代码：`006131`
- 数据日期：`2026-08-31`
- 当时尚未提交的 Tool 签名：`get_fund_brief(fund_code)`
- 模型链路：GLM-5.2 经硅基流动的 OpenAI-compatible Chat Completions 接入 OpenAI Agents SDK

## 实际输出

第一轮只看到：

```text
Agent 未调用 get_fund_brief，拒绝生成基金晨报
```

但检查 `new_items` 后发现 Model 实际已经发出 Tool Call：

```text
ReasoningItem
ToolCallItem
ToolCallOutputItem(output=str)
ReasoningItem
MessageOutputItem
```

继续查看工具输出摘要，才看到真正原因：

```text
Invalid JSON input for tool get_fund_brief
```

## 期望行为

根据 `docs/fund_morning_brief_mvp.md` 的 Agent 工作链路，`006131` 应由 Python 读取、校验和计算，Model 只解释工具返回的结构化结果。

因此程序应做到：

1. 当前单基金版本不要求 Model 再填写已经确定的基金代码；
2. Tool Call 参数解析失败时，不能误报为“Model 没有调用工具”；
3. 失败时继续阻断晨报，不能退回到 Model 自行生成数字。

## 影响与风险

- 可用性：数据正常、指标可算，但晨报无法生成。
- 可诊断性：错误文案把 SDK 入参失败说成没有 Tool Call，可能诱导开发者错误修改 Prompt。
- 数据安全：如果为了绕过失败而直接采用 Model 输出，可能破坏“Python 独占确定性数字”的核心边界。

## 根因

```text
Model 发出带参数的 Tool Call
→ arguments 未通过 SDK 的 JSON / Tool Schema 校验
→ Python 工具函数没有真正执行
→ ToolCallOutputItem 保存错误文本
→ json.loads() 解析失败并跳过
→ 程序把提取失败笼统描述为没有调用工具
```

MVP 当时只支持 `006131`，基金代码已经由命令行和 Python 确定，却又让 Model 在 Tool Schema 中重复填写。这增加了不必要的失败面。

## 处理方案

将职责调整为：

```text
命令行输入基金代码
→ Python 验证是否为 006131
→ Agent 调用无参数 get_fund_brief()
→ Tool 内使用 SUPPORTED_FUND_CODE
→ Model 只解释返回结果
```

具体改动：

- `fund_agent.py`：将 `get_fund_brief(fund_code)` 改成无参数工具；
- `fund_main.py`：在调用 Agent 前由 Python 拒绝不支持的基金代码；
- 保留 `build_fund_brief(fund_code)` 的代码校验，避免底层函数失去保护；
- 提取失败时统一使用更准确的“未返回有效基金工具结果”，不再断言 Model 没发出 Tool Call。

## 回归验证

修复后实际运行：

```text
python -B fund_main.py 006131
```

结果完成以下链路：

```text
无参数 Tool Call
→ normal + completed
→ Model 三段解释
→ Python 二次校验
→ output/fund_brief.html
```

当前 59 条自动化测试全部通过，真实端到端运行和 HTML 浏览器检查也已通过。

## 遗留限制

- 尚未针对 `ToolCallOutputItem.output` 中的 SDK 错误文本建立专门的错误分类测试。
- `extract_fund_brief()` 仍把多类提取失败合并为“未返回有效结果”，诊断精度有限。
- 未来扩展多基金时，不应简单把必填 `fund_code` 重新交给 Model；应由 Python 编排层注入目标代码。
