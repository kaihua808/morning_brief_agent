# BC-001｜基金指标程序未校验数据新鲜度，仍将过期净值作为当前指标输出

> 状态：已解决
> 发现日期：2026-08-31
> 归因层：产品规格缺口，随后补齐实现与测试

## 发现来源

真实使用。运行 `fund_metrics.py` 时发现，本地 CSV 的最新净值日期停留在 `2026-08-20`，但程序仍把它作为近期数据计算并输出指标。

## 触发条件

- 代码版本：`a72bf86 Improve workflow and add fund metrics`
- 运行日期：2026-08-31
- 基金代码：`006131`
- 数据快照：最新日期为 `2026-08-20`
- 当时入口：`python fund_metrics.py`

当时的程序直接读取 CSV 并计算指标，没有参考日期、新鲜度状态或阻断分支。

## 实际输出

原始终端输出当时没有保存，因此不伪造原文。使用保留下来的延迟固件可以复现当时的数据条件：

```text
数据日期：2026-08-20
运行日期：2026-08-31
相差：11 个自然日
```

旧程序仍会计算近 5 日、近 20 日、区间位置和最大回撤，并把这些历史结果展示成当前分析。

修复后使用同一固件得到：

```text
data_status: delayed
calculation_status: blocked
metrics: null
error: 基金数据已过期，请更新后重新分析
```

## 期望行为

发现问题后形成的 MVP 规格明确写入 `docs/fund_morning_brief_mvp.md`“三分钟晨报输出”：数据不是最新可确认交易日时，应先提示异常，不继续生成确定性解读。

需要说明：该规格是在真实问题暴露后才被正式沉淀，因此本条不是“已有规格被代码违反”，而是一次真实使用推动产品边界完善的 badcase。

## 影响与风险

过期数据本身不一定错误，危险在于用户不知道它已经过期。以保留的数据为例，`2026-08-20` 快照计算出的近 5 日、近 20 日变化分别为 `-1.42%`、`-2.31%`；刷新至 `2026-08-31` 后相同指标变为 `+1.35%`、`+1.82%`。

两个观察窗口的方向都发生反转。如果程序不显示日期并阻断旧数据，用户可能把上一阶段的下跌误认为当前趋势，进而干扰研究和个人判断。

## 根因

当时的代码把“CSV 能读取”错误地等同于“数据可用于今天的晨报”：

```text
读取 CSV
→ 直接计算指标
→ 直接输出
```

缺少三层保护：

1. 数据日期与参考日期的比较；
2. `normal / delayed / missing / insufficient / invalid` 状态；
3. 异常状态阻止计算和 Model 解读。

## 处理方案

- 在 `build_fund_brief()` 中加入数据日期、新鲜度和字段校验；
- 延迟数据返回 `delayed + blocked`，不返回指标；
- 保留 `data/fixtures/006131_delayed.csv` 作为稳定回归固件；
- 增加安全自动刷新：候选数据校验失败时不覆盖原 CSV；
- Agent 只在 `normal + completed` 时进入 Model 解释；
- “为什么选择阻断”记录在 [ADR-001](ADR-001.md)。

## 遗留限制

- 新鲜度当前按自然日判断，春节、国庆等长假可能误报；后续应接入交易日历。
- 刷新失败目前一律阻断，即使本地文件仍在可接受时效内也不会降级使用。
- 正式 CSV 仍被 Git 跟踪，后续应把运行缓存与测试固件分离。
